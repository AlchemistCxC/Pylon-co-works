# 新建会话后删除导致用户数据同步失败：定位与修复方案

## 1. 问题现象

操作路径：

1. 打开 Pylon。
2. 新建一个本地会话。
3. 删除该会话。

随后出现两类提示：

- `同步用户数据到后端失败（sessions）`，错误信息中包含 `revision`，但当前 UI 展示内容被截断。
- `配置未能保存到本地存储（本次操作仅在内存生效）`。

本次只完成源码定位与修复文档落盘，不直接修改业务代码。

## 2. 结论

根因是同一份 `sessions` 用户数据被两条独立写入链修改，但前端 `UserDataRepository` 的 revision baseline 没有在会话删除 IPC 完成后同步推进：

- 删除会话的后端命令 `user_session_delete` 会直接修改 SQLite 的 `user_data.sessions` envelope，并使其 revision 增加。
- 删除完成后，前端 `identityStore.removeSession` 又把删除后的完整 sessions 快照通过 `syncIdentityToBackend()` 写回。
- `syncIdentityToBackend()` 使用的 `UserDataRepository` 仍持有删除前的旧 revision。
- 后端以旧 revision 作为 `expectedRevision` 时拒绝写入，返回 `user_data_revision_conflict`。
- 该失败被统一写入 `identityPersistence.sessions = 'degraded-readonly'` 和 `lastPersistError`。
- 布局层只判断 `lastPersistError` 是否存在，统一显示为“本地存储失败”，因此第二条提示的实际含义并不准确：这里主要是后端 SQLite revision 冲突，不是浏览器 `localStorage` 写入失败。

## 3. 源码验链

### 3.1 删除事务的调用顺序

文件：`src/application/transactions/removeSessionTransaction.ts`

当前顺序：

```text
removeSessionTransaction
  ├─ deleteSessionLocal(session)
  ├─ markSessionDeleted(id)
  ├─ removeSession(id)
  ├─ clearMessages(id)
  ├─ closeSession(session)       // best effort
  └─ finalizeSessionDelete(session) // best effort
```

对应位置：

- `removeSessionTransaction.ts:43-49`：先调用 `deleteSessionLocal`。
- `removeSessionTransaction.ts:50-53`：本地删除成功后调用 `removeSession`。
- `removeSessionTransaction.ts:54-64`：随后执行远端 close 与删除终态化。

### 3.2 删除会话的实际前端 IPC

文件：

- `src/components/Sidebar.tsx:65-70`
- `src/components/SessionSettings.tsx:81-87`

两处都调用：

```ts
invoke('user_session_delete', {
  sessionId: s.id,
  ownerKey: sessionDurableOwnerKey(s),
})
```

### 3.3 删除 IPC 会直接修改 user_data.sessions

文件：`src-tauri/src/session/mod.rs`

- `mod.rs:730-738`：`user_session_delete` 命令入口。
- `mod.rs:697-714`：`delete_session_core` 先调用用户数据删除，再创建会话 tombstone。
- `mod.rs:702-707`：调用 `UserDataService.delete_session(session_id)`。

文件：`src-tauri/src/session/user_data.rs`

- `user_data.rs:512-548`：`delete_session` 从 `sessions` envelope 移除目标会话，并执行 `revision + 1` 后写回 SQLite。

关键行为：

```text
user_session_delete
  └─ user_data_service.delete_session(session_id)
       └─ sessions envelope revision 增加
```

这不是只删除消息或运行时状态，而是直接改变了与 `UserDataRepository.save('sessions', ...)` 共用的 `user_data` 表。

### 3.4 删除后的前端二次写回

文件：`src/identityStore.ts`

- `identityStore.ts:535-555`：`removeSession` 从内存 sessions 移除目标会话，调用 `persistMergingUnresolved(...)` 写 localStorage，并在 `identityMutationSeq` 增加后执行 `queueMicrotask(syncIdentityToBackend)`。
- `identityStore.ts:803-849`：`syncIdentityToBackend` 调用 `userDataRepository.save('sessions', ...)`，携带完整 sessions 快照。
- `identityStore.ts:835-839`：实际写入 `sessions` envelope。

因此删除路径实际是：

```text
user_session_delete
  └─ SQLite sessions revision: N → N+1

removeSession
  └─ UserDataRepository.save(sessions, expectedRevision=N)
       └─ 后端当前 revision=N+1
            └─ user_data_revision_conflict
```

### 3.5 repository baseline 没有被删除命令结果推进

文件：`src/userDataRepository.ts`

- `userDataRepository.ts:117-128`：每个 key 持有独立 `baseline`。
- `userDataRepository.ts:145-224`：`scheduleSave` 依据 `queue.baseline` 发送 `expectedRevision`，成功后才用 save 返回值推进 baseline。
- `userDataRepository.ts:212-220`：revision conflict 后只尝试重新 load baseline，并将错误抛给上层。
- `userDataRepository.ts:225-241`：`load` 可以刷新 baseline，但删除会话事务没有调用 repository 的 load 或专用 baseline 更新接口。

删除 IPC 返回值当前是 `void`，没有返回 `sessions` 新 revision，也没有通知前端 repository 更新 baseline。因此 repository 不知道后端已经在删除命令内部推进过 revision。

## 4. 为什么会同时出现“本地存储失败”提示

文件：`src/identityStore.ts`

- `identityStore.ts:213-217`：`persistFlag` 把同步失败统一记录为 `配置未能保存到本地存储`。
- `identityStore.ts:809-815`：后端同步失败时设置：
  - `lastPersistError = 'SQLite 用户数据同步失败；已切换为只读，请重试恢复'`
  - `identityPersistence.sessions = 'degraded-readonly'`
- `src/workspace-sheets/SheetLayout.tsx:118-123`：只要 `workspacePersistError` 或 `identityPersistError` 存在，就显示：

```tsx
配置未能保存到本地存储（本次操作仅在内存生效）
```

所以该提示是“持久化失败”的泛化文案，不足以区分：

- 真正的 localStorage `setItem` 失败；
- Tauri 后端 SQLite 不可用；
- `user_data_revision_conflict`；
- 其他用户数据后端错误。

当前现象中，删除会话后本地 `persistSessionsWithUnresolved` 已在 `removeSession` 内调用，且其失败只会在 `localStorage.setItem` 抛异常时返回 `false`。从调用关系看，触发警告的主要来源是后续后端同步失败，而不是本地存储本身。

## 5. 最小、低破坏修复方案

目标：保留现有“本地优先删除”和 revision 乐观并发架构，不改动删除顺序，不绕过后端 authority。

### 方案 A：删除命令返回 sessions 新 revision，并由 repository 原子接收

推荐方案。

#### 后端

将 `user_session_delete` 的返回值从 `Result<(), UserDataError>` 改为包含新 revision 的结果，例如：

```rust
pub(crate) struct SessionDeleteResult {
    pub(crate) sessions_revision: i64,
}
```

`delete_session_core` 返回 `UserDataService.delete_session(session_id)` 的 revision；tombstone 写入仍保持原有逻辑。

#### 前端 repository

在 `UserDataRepository` 增加一个只推进指定 key baseline 的内部能力，例如：

```ts
ackExternalWrite(key: UserDataKey, revision: number): void
```

语义要求：

- 只允许把 baseline 向前推进，不允许回退；
- 若同 key 当前存在更近的在飞写/排队写，不能覆盖其 pending payload；
- 不改变现有 per-key 串行队列；
- 仅用于明确知道后端已经完成写入的命令结果。

#### 删除事务接线

将 `deleteSessionLocal` 的返回值改为读取删除结果：

```ts
const deletion = await invoke<SessionDeleteResult>('user_session_delete', ...)
userDataRepository?.ackExternalWrite('sessions', deletion.sessionsRevision)
```

然后继续执行现有的 `removeSession(id)`。这样后续 `syncIdentityToBackend` 即使继续发送完整快照，也会使用删除后 revision `N+1`，不会产生自致冲突。

注意：如果当前删除命令已经在 repository 的 sessions 写队列之后排队执行，`ackExternalWrite` 必须纳入该 key 的串行队列，不能简单地无条件覆盖 baseline。更稳妥的实现是提供 repository 级方法：

```ts
ackExternalWrite(key, revision): Promise<void>
```

该方法等待当前 key 队列落定后再推进 baseline；若发现待写快照基于更旧状态，则按现有 latest-wins 规则继续发送最新快照。

### 方案 B：删除 IPC 完成后强制 repository load

改动更小，但多一次 IPC 读取：

```text
user_session_delete 成功
  └─ userDataRepository.load('sessions')
       └─ 刷新 baseline
  └─ removeSession(id)
       └─ syncIdentityToBackend
```

优点：不扩展后端 DTO，直接复用现有 `load` baseline 刷新语义。

缺点：

- 删除流程额外增加一次 SQLite 读取；
- 如果 `load` 与后续 mutation 的队列调度不严谨，仍需验证不会把新快照覆盖掉；
- 删除命令已经知道 revision，却没有直接返回，协议表达不完整。

该方案可作为热修复或方案 A 上线前的过渡，不建议作为长期契约。

### 方案 C：删除后不再调用 `removeSession` 的后端同步

不推荐。

这会让删除命令和前端内存状态形成两套特殊语义，容易使 turns、unresolved session、localStorage 镜像与后端 envelope 分叉，破坏现有“所有 identity mutation 统一走完整快照同步”的架构纪律。

## 6. 文案与错误状态的配套修正

这不是本次 revision 根因的必要修复，但应一并纳入后续实现，避免误导用户。

### 6.1 分离错误来源

建议将 `lastPersistError` 细化为结构化状态，至少区分：

```ts
type IdentityPersistFailure =
  | { source: 'local-storage'; message: string }
  | { source: 'backend'; domain: 'profiles' | 'sessions'; code?: string; message: string }
```

当前 `identityStore.ts:809-815` 已经保留了 backend error 的入口，应该将 `UserDataRepositoryError.code` 一并传入，而不是只显示统一字符串。

### 6.2 UI 按来源显示

`SheetLayout.tsx` 不应把所有 `lastPersistError` 都渲染为“本地存储失败”。建议至少显示：

- localStorage 失败：`配置未能保存到本地存储（本次操作仅在内存生效）`
- SQLite unavailable：`用户数据服务暂不可用，配置尚未同步到后端`
- revision conflict：`用户数据已被其他写入更新，当前修改尚未同步；请重试`

这样可以避免把后端并发错误误判为浏览器存储容量或权限问题。

## 7. 修复后应验证的行为

本次文档阶段不执行修复和测试。后续实施时至少验证：

### 单元/集成层

1. `user_session_delete` 返回删除后的 `sessions_revision`。
2. 删除后 repository baseline 等于删除后的 revision。
3. 删除后 `removeSession` 触发的完整 sessions 快照写入使用新 revision，不出现 `user_data_revision_conflict`。
4. 重复删除、sessions envelope 不存在、删除命令失败时，原有幂等与错误语义不变。
5. 删除期间若存在其他 pending mutation，latest-wins 与 per-key 串行仍成立。

### 前端网页层

1. 新建会话。
2. 删除会话。
3. 会话从侧栏移除，消息快照清理。
4. 不出现“同步用户数据到后端失败（sessions）”。
5. 不出现错误的“本地存储失败”提示。
6. 刷新应用后被删除会话不会复活。

### 真实 Tauri 应用层

1. 在真实 Tauri + SQLite 环境重复上述流程。
2. 采集 `user_session_delete` 与 `user_data_save` 的 IPC 日志，确认 revision 链为：

```text
删除命令推进 sessions revision: N → N+1
后续完整快照保存 expectedRevision: N+1
保存成功 revision: N+2
```

3. 关闭并重新打开应用，确认 SQLite 中会话确实不存在。
4. 确认本地 localStorage 镜像与 SQLite authority 都不再包含该会话。

## 8. 建议实施顺序

1. 先实现方案 A 的后端删除结果 DTO与前端 repository baseline 接收能力。
2. 再接通 Sidebar 与 SessionSettings 两个删除入口。
3. 增加删除后 revision 链测试。
4. 最后拆分 backend/localStorage 错误状态与 UI 文案。

本次定位结论：优先修复“删除 IPC 直接推进 revision，但 repository baseline 未同步”的契约断裂；不要删除后端二次同步，也不要把问题归因于 localStorage 容量或浏览器存储权限。
