# 1. 前端开发准则、状态模型、提交协议和交接规则

## 1.1 开发准则

1. **先读源码，不猜 UI 或数据流**：当前 `src/**`、`scripts/**` 和后端手册优先于历史文档。
2. **前端边界**：前端 coder 修改 `src/**`、`scripts/**`、必要的 `package.json` 和本文档；未经授权不修改 `src-tauri/**`、`agents.yaml`、Peri 或 Prism 源码。
3. **保留已有设计**：用户未要求改动的视觉、主题、Control Center、Chat、Pet 行为不动。
4. **CSS 同步删改**：删除组件、class 或状态时同步清理死 CSS 和过期测试。
5. **状态单一真值**：Session 集合只通过 store actions 和 `sessionPersistence.ts`；主题只通过主题 action；Workspace Sheet 使用独立 versioned persistence，不写入 `pylon-theme`。
6. **前后端契约不脑补**：后端 command/event 不存在时，UI 隐藏或标记未接入，不使用 mock 冒充产品功能。
7. **浏览器不等于 Tauri**：浏览器 mock 只验视觉和纯前端行为；真实 Agent、Workspace、Prism、Runtime 必须用 Tauri 验收。
8. **Session 身份不可混用**：`Session.id → source → periId` 三层必须沿现有 adapter 处理。
9. **右栏不成为第二应用区**：右栏只承载当前 Sheet 的 Context Inspector；完整日志、Diff、Git History、Prism 管理进入 Sheet。
10. **无障碍和键盘优先**：Launcher、Tab、关闭、右键菜单、Dialog 必须具备键盘和可见 focus。
11. **不制造半吊子功能**：占位 Reserved Tab、无 handler 按钮、写入 localStorage 但不进入 runtime 的设置都不能算完成。
12. **真实执行收尾**：改代码后必须 fresh 执行 targeted tests、前端 runner、build 和 diff check；浏览器/Tauri证据分开报告。

## 1.2 当前前端架构事实

顶层：

- `src/App.tsx` 维护 `activeSession`、Settings、Profile、SessionSettings、Sidebar 折叠、右栏和当前活动 Sheet。
- `src/store.ts` 混合 Theme、Profile、Session、Agent status、按 source 隔离的 runtime state，以及独立 Sheet actions/state。
- `src/sessionPersistence.ts` 独立持久化 Session 集合到 `pylon-sessions`。
- `src/components/chat/ChatView.tsx` 负责 Tauri event、replay、messages、tool/reasoning/usage 渲染。
- `src/components/ControlCenter.tsx` 使用 v3 slot layout、per-widget scale 和 Session runtime。
- `src/components/RightPanel.tsx` 已接 Workspace/Logs，另有两个 Reserved Tab。
- `src/components/PrismSheet.tsx` 仍是静态演示数据。
- `src/components/PetCompanion.tsx` 已接 `get_pet/pet_action`，浏览器使用 mock。

当前后端事实：

- 只有一个 active runtime Agent。
- 多个 Agent Sheet 在 B7 前只是多个前端工作现场；聚焦不同 Agent Sheet 需要 `switch_agent`，后端会清空内存 Session mapping。
- Workspace/Runtime 基础 command 已存在。
- Prism command 当前后端工作区开发中且已发现 method/query/body 不一致；对应后端 B3，前端不得直接假设最终 DTO。
- Git 只读对应后端 B5；PTY、Runs 与 Git 写操作对应 B8；多 Agent 并行对应 B7。

## 1.3 身份与状态不变量

```text
sheetId              Workspace Sheet 本地实体
agentId              Agent registry key
Session.id           Zustand/消息缓存 owner
Session.source       Tauri command/event scope
Session.periId       ACP 远端 sessionId
```

Sheet 和 Session 层级：

```text
Workspace
└── Agent Sheet
    ├── agentId
    ├── activeProfileId
    ├── activeSessionId
    ├── input draft / scroll state
    ├── right panel state
    └── Sidebar Session list
```

约束：

- Sheet state 不替代 Session store。
- 非当前 Sheet 的 Chat/Control Center 是否保持 mounted 必须显式设计；不得因切 Tab 丢输入草稿或把旧 event 写到新 Session。
- 后端仍单 active runtime 时，非活动 Agent Sheet 必须显示 inactive，不得显示 connected 假状态。

### 状态标注规则

1. **接手时标注一次**：执行一次 Git/源码检查，修正将要执行的大任务状态和“下一动作”。
2. **大任务进行中**：开始开发后把大任务标为“开发中”，在正文记录当前正在处理的子任务编号。
3. **源码完成但缺真实证据**：大任务或能力标为“待验收”，并移入第 3 章；不得写成“已完成”。
4. **阻塞必须写解除条件**：例如“等待后端 B3.1 修正 Prism 路由”，不能只写“等待后端”。
5. **大任务完成时统一标注**：只更新一次本表、该大任务正文、第 3 章验收区和第 5 章交接记录。
6. **已验收能力不保留流水账**：从任务队列删除，在第 4 章保留稳定源码/API 索引和最终证据入口。
7. **同一能力状态唯一**：不能在待开发区写“待开发”，同时又在验收区写“待验收”。
8. **新增任务必须完整说明**：为什么做、当前源码事实、交付结果、非目标、依赖/阻塞、验证、状态迁移条件。

## 1.7 Git 检查、提交与连续执行规则

### 接手检查：一次即可

一轮前端接手开始时执行一次：

```bash
git status --short --branch
git log -5 --oneline
git diff -- src scripts docs/前端开发与交接手册.md
git diff --cached
```

目的：确认当前 HEAD、识别他人改动、核对本文状态是否过期、划定本轮大任务文件边界。除非发生外部改动、冲突、切换大任务或准备提交，不在每个子任务前重复整套检查。

### 默认模式

1. 用户要求执行一个大任务时，从正文标记的“当前子任务”或第一个未完成子任务开始。
2. 同一大任务内连续实现和验证各子任务，不逐项询问、不逐子任务 commit。
3. **一个大任务只 commit 一次。** commit 包含该大任务的生产源码、测试、必要 CSS、runner/fixture 和本文状态更新。
4. **一个大任务只做一次正式交接标注。** 统一更新第 1.5 节状态总览、该大任务正文和必要的第 3 章验收项。
5. 完成整个大任务后停止，统一汇报：大任务 commit、完成子任务、自动测试、浏览器/Tauri 边界和检查节点。

### 连续多个大任务模式

1. 每个大任务各自一次 commit，不把多个大任务压成一个 commit。
2. 大任务完成提交和状态标注后，继续用户授权范围内的下一大任务。
3. 到达 `CP-F*` 时执行节点验证、更新本文并报告可上线范围。
4. 用户未明确允许跨检查节点持续时，在检查节点暂停。
5. 需求或后端契约不明确时，标注阻塞和解除条件，顺延其他可执行任务；不得用 mock 填补。

### 验收型大任务

只做浏览器/Tauri 验收时：

- 有可重复 runner/fixture：纳入该大任务一次性 commit。
- 只有人工证据：更新本文和证据索引，仍作为该大任务一次性 commit。
- 不因“没有业务源码修改”恢复逐验收项提交；不同大任务也不得混提。

### Commit 规则

```text
feat(frontend): F0 完成 Workspace Sheet 基础
fix(frontend): F1 收敛右栏 Context Inspector
feat(frontend): F2 接入 Prism 管理 Sheet
test(frontend): F6 建立可重复前端验收
refactor(frontend): F7 收敛主题与 Control Center
```

只显式 stage 当前大任务文件。禁止 `git add .`、`git add -A`、reset、clean、restore。

## 1.8 每个大任务的固定执行链

```text
1. 接手时执行一次 Git 检查，确认状态和大任务边界
2. 读取目标组件、store、adapter、CSS、tests 与对应后端契约
3. 按子任务顺序建立 failing pure/behavior test
4. 逐项最小实现并运行 targeted test
5. 子任务间只做必要局部验证，不 commit、不重复整套准备流程
6. 大任务完成后统一运行 npm run test:frontend
7. 统一运行 npm run build
8. 统一执行浏览器验收（UI/几何任务）
9. 统一执行真实 Tauri 验收（invoke/event 任务）
10. 运行 git diff --check -- 当前大任务文件
11. 更新第 1.5 节状态、任务正文、验收缺口和下一动作
12. 提交前再次检查限定 diff，显式 stage 当前大任务文件
13. 为整个大任务创建一个 commit
14. commit 后确认无本任务残留，再汇报或进入下一大任务
```

`npm run test:frontend` 当前 runner 的 `allowedFailures` 为空；仍必须记录真实失败和 excluded 跨端脚本，不能只看聚合 exit code。任何源码、测试、CSS 或文档修改都会使之前验证证据 stale。

## 1.9 上线检查节点定义

检查节点要求：

- 节点范围内所有大任务已 commit。
- 当前发行入口没有半接线 UI、无 handler 按钮、伪 mock 数据或损坏 migration。
- 自动回归/build 通过；仍 allowed failure 必须不覆盖节点关键功能。
- 浏览器几何和真实 Tauri 依赖按节点要求验收。
- 后端未完成能力被隐藏或明确不可用。
- 旧 localStorage/session/profile 数据有 migration 或安全 fallback。

## 1.10 交接文档迁移与标注规则

每完成一个大任务：

1. 在第 1.5 节更新一次：状态、当前阶段、下一动作、commit 和仍缺证据。
2. 在该大任务正文统一标注全部子任务结果，不为每个子任务重复写交接流水账。
3. 源码完成但缺浏览器/Tauri/真实后端证据的能力，合并到第 3 章验收区。
4. 真实验收完成后，从验收区删除，在第 4 章保留稳定能力索引。
5. 不允许同一任务同时以冲突状态出现在开发区和验收区。
6. 新增任务必须分配唯一编号，并写完整任务说明和状态迁移条件。
7. 后端大任务编号变化时，必须同步所有前端“后端依赖”引用和第 4.2 节 API 依赖。
8. 下一位 coder 先看状态总览，再做一次实时 Git/源码核对；不得从旧 commit 或 skill 猜当前进度。

# 5. 下一位 coder 的接管顺序

## 5.1 一次性接管流程

1. 先读第 1.5 节状态总览，确认用户指定或当前最高优先级大任务。
2. 仅在接手开始时执行一次：

```bash
git status --short --branch
git log -5 --oneline
git diff -- src scripts docs/前端开发与交接手册.md
git diff --cached
```

3. 对照总览、目标大任务正文和当前源码，修正文档中过期状态。
4. 识别前端、后端、文档和其他 coder 改动归属；不覆盖、不 reset、不全量 stage。
5. 读取目标任务需要的 `src/**`、`scripts/**` 和后端对应 B 编号。Skill 只用于定位路径和工具，不用于判断进度。
6. 按第 1.8 节连续执行该大任务的子任务；子任务间不逐项 commit、不重复整套 Git 准备检查。
7. 大任务完成后统一执行测试、build、浏览器/Tauri 验收，更新状态总览、正文和验收区。
8. 提交前再次检查限定 diff，显式 stage 当前大任务文件，创建一个大任务 commit。
9. commit 后确认无本任务残留；默认停下汇报。用户授权连续大任务时再进入下一项。

新缺口不能只追加一句 TODO：

```text
### Fx.y 任务名称

状态：待开发/开发中/待验收/阻塞，优先级。
为什么做：用户问题、风险或产品缺口。
当前源码事实：文件与稳定符号、已有能力、缺失环节。
交付结果：完成后的可观察行为、组件/状态/API。
实现范围：允许修改的模块和必须保持的不变量。
明确非目标：本任务不处理的相邻能力。
前端依赖：前置 F 编号。
后端依赖/阻塞：B 编号、command/event、解除条件。
验证：pure/runner/build/浏览器/Tauri 各证明什么。
大任务内文件边界：预计文件；不代表单独 commit。
状态迁移：进入待验收或删除任务的条件。
```

拆分规则：

- 按可验证用户结果拆，不按文件数量拆。
- `store/action → adapter → component → CSS/DOM → browser → Tauri` 可以作为子任务层次，但紧密服务同一结果时属于同一大任务。
- 已被真实 UI 调用的能力优先修契约和错误状态，不重新做一套 mock。
- 浏览器验收与真实 Tauri 验收分别标注；build 通过不能关闭运行时验收。
- 新任务加入后同步第 1.5 节的状态、当前阶段和下一动作。
