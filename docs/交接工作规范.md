# 交接工作规范

## 1. 目的

本规范约束 coder 在 Pylon 项目中完成开发、修复或审计后，如何提交可验证、可接管的交接清单。

交接不是开发日志，也不是一句“已完成”。交接必须让下一位 coder 在不依赖口头上下文的情况下，能够确认：

- 改了什么。
- 为什么改。
- 修改边界在哪里。
- 哪些内容已经验证。
- 哪些内容没有验证。
- 当前工作区是否包含他人修改。
- 下一步如何继续。

---

## 2. 项目边界

项目路径：

```text
G:\Project\prism-desktop
```

技术栈：

- Tauri v2
- React 19
- TypeScript 5
- Vite 6
- Zustand
- Radix UI
- 纯 CSS + CSS Variables

### 2.1 默认修改范围

前端任务默认仅允许修改：

```text
src/
scripts/
docs/
```

### 2.2 后端边界

未经任务明确授权，不修改：

```text
src-tauri/
```

如果任务需要跨层能力，coder 必须先在交接中写清：

- 前端需要的 command/event。
- 当前后端是否已存在。
- 参数和返回结构。
- 是否需要后端 coder 配合。

不得用前端 mock 或 localStorage 伪装后端功能已接入。

### 2.3 既有工作区保护

开始前必须执行：

```bash
git status --short
git branch --show-current
git log -1 --oneline
```

交接中必须列出开始时已经存在的修改。

原则：

- 不覆盖用户已有修改。
- 不把用户已有修改纳入自己的 commit。
- 不擅自删除未跟踪文件。
- 不执行 `git reset --hard`、`git clean -fd`。
- 不把其他 coder 的修改冒充成自己的产出。

## 3. Coding 规范

## 3.1 先读源码，不猜

修改前必须追踪完整链路：

```text
交互入口
→ React state/store
→ persist/migration
→ Tauri invoke/listen
→ renderer 消费
→ 错误/切换/删除路径
```

报告根因时引用当前源码的文件和行号。历史 Markdown、旧 Bug List、旧 commit 只可作候选线索，不能代替当前源码。

## 3.2 单一真值

同一业务状态只能有一个主真值。

示例：

- Session 集合：统一通过 store action + `sessionPersistence.ts`。
- Session runtime stats：按 source/session 保存，不使用一份全局值表示所有会话。
- 中控区布局：`ccLayout` 是几何真值，不恢复第二套 runtime override。
- Prompt preset：独立资产 store，不塞进 ThemeSettings。

禁止：

- 同一集合同时写 Zustand persist 和独立 localStorage。
- JSX 渲染中用 `useStore.getState()` 替代响应式订阅。
- 给同一设置建立两个互相覆盖的字段。

## 3.3 前端状态作用域

新增状态前必须标注作用域：

- 全局 App
- Agent
- Profile
- Session
- 单次 generation
- 纯 UI 瞬时状态

Session 级数据必须按 `source` 或稳定 session ID 隔离。不能用一份全局字段跨会话复用。

## 3.4 Zustand 规范

- 渲染组件使用 `useStore(selector)`。
- 事件回调可使用 `useStore.getState()` 获取最新状态。
- `useShallow` selector 必须列出所有参与渲染/CSS variable 计算的字段。
- 新增持久化字段时同步检查：
  - DEFAULTS
  - ThemeSettings/type
  - partialize
  - migrate/normalize
  - presets/custom presets
  - App CSS variable 注入
  - Settings UI
  - renderer 消费

## 3.5 异步与会话切换

所有异步结果都必须校验所有权：

- 请求开始时的 session ID/source。
- 请求 generation/epoch。
- 响应到达时是否仍属于当前实体。

不得让旧会话 load、旧 Agent response 或旧设置请求覆盖当前界面。

乐观更新必须有失败回滚。

## 3.6 ACP/Tauri 契约

- 为 command response 和 event payload 建立 TypeScript 类型。
- `invoke()` 参数名必须与 Tauri command 参数一致。
- notification 与 request response 分开处理。
- 未知 ACP variant/type 必须安全降级，不能 `unreachable` 或强制 cast。
- ACP config options 优先动态渲染，不硬编码为某一个 Agent 专用字段集。
- 前端不得宣称未接入运行时的设置已生效。

## 3.7 UI 与 CSS

- 不改变用户未要求修改的设计。
- 使用现有 CSS Variables 和 uiScheme。
- 删除 DOM 时同步删除死 CSS。
- 新增 CSS 后检查浅色/深色。
- `<pre>`、`<code>` 显式使用终端字体。
- naturalSize widget 不依赖父级百分比高度。
- 瞬时错误提示使用浮层，不推挤布局。
- 交互元素使用原生 button/input/select，或补齐 role/tabIndex/键盘交互。
- `prefers-reduced-motion` 覆盖新增动画。

## 3.8 命名与注释

- 标识符用英文。
- 注释用中文，解释“为什么”，不重复代码字面意思。
- 不保留过时注释。
- 不在正式代码注释中使用 emoji 装饰。
- 类型名、action 名、event 名应体现作用域。

## 3.9 错误处理

禁止无理由吞错：

```ts
.catch(() => {})
catch {}
```

允许吞错的场景仅限明确 best-effort cleanup，并应有注释。

用户可操作失败必须进入可见错误 UI；诊断信息进入日志。

## 3.10 测试规范

Bug 修复必须有回归测试或可重复的运行时验证。

测试分级：

1. 纯函数测试：状态转换、migration、payload 构造。
2. 源码结构断言：只用于防漏，不能代替行为测试。
3. 浏览器 UI：验证布局、CSS、DOM 和可访问性。
4. Tauri runtime：验证 invoke/listen、Agent、ACP、文件路径。
5. 日志/抓包：验证跨层事件时序。

不能用浏览器中的 Tauri runtime 缺失错误判定真实后端失败。

## 4. Commit 规范

### 4.1 一个 commit 一个根因

示例：

```text
fix(chat): 保留空 replay 时的本地历史缓存
fix(runtime): 按 source 隔离上下文统计
fix(pet): 区分点击双击与拖拽状态
refactor(settings): 重排会话设置表单层级
```

禁止把以下内容混入同一 commit：

- Bug 修复 + 无关 UI 美化。
- 前端修复 + 后端重构。
- 多个独立根因。
- 用户已有工作区修改。

### 4.2 提交前检查

```bash
git diff --check -- src scripts docs
git diff --stat
git status --short
```

提交前明确 staged 文件：

```bash
git diff --cached --name-only
```

## 5. 交接清单必须包含的内容

每次交接至少包含以下章节。

## 5.1 任务摘要

一到三句话说明本轮目标和最终结果。

示例：

```text
修复历史会话进入后空 replay 覆盖本地缓存的问题，并将恢复态与生成态分离。未修改后端协议。
```

## 5.2 修改范围

按“新增 / 修改 / 删除”列出文件：

```text
新增：
- src/components/chat/sessionReplayState.ts
- scripts/test-session-replay-state.mts

修改：
- src/components/chat/ChatView.tsx

删除：
- 无
```

必须说明每个文件承担的职责，不只列路径。

## 5.3 根因

Bug 交接必须写：

- 触发条件。
- 实际表现。
- 根因链路。
- 为什么原有逻辑会失败。

不得只写“修复状态问题”。

## 5.4 实现说明

描述关键实现和不变量：

- 新增了什么状态/action/type。
- 数据所有权在哪里。
- 异步如何防止旧响应覆盖。
- 失败如何回滚。
- migration 如何兼容旧数据。

## 5.5 验证证据

必须记录真实执行的命令和结果：

```text
node --experimental-strip-types scripts/test-session-replay-state.mts
结果：通过，exit code 0

npm run build
结果：通过，exit code 0
Vite warning：...
```

不要只写“测试通过”。

运行时验证必须包含：

- 复现步骤。
- 预期。
- 实际。
- 日志/event/localStorage/DOM 几何等证据。

未执行的测试明确写“未执行”，不能省略。

## 5.6 当前 Git 状态

交接结束前重新执行并记录：

```bash
git status --short
git log -1 --oneline
```

区分：

- 本轮提交。
- 用户原有修改。
- 其他 coder 修改。
- 未跟踪文件。

## 5.7 已知问题与未完成项

每项必须说明：

- 为什么没做。
- 是否被当前任务阻塞。
- 下一步需要什么输入或权限。
- 风险级别。

不得用“后续优化”笼统带过。

## 5.8 下一步

给出下一位 coder 可执行的动作：

```text
1. 在真实 Tauri 环境创建 A/B 两个 session。
2. A 生成时切到 B，记录 peri:update source。
3. 验证 sessionLiveStats[A] 持续更新且 B 不显示 A 数据。
```

## 5.9 边界声明

明确说明：

- 是否修改后端。
- 是否修改依赖。
- 是否修改设计。
- 是否执行 commit。
- 是否启动长期进程。

## 9. 禁止项

交接中禁止：

- 伪造测试输出、日志、commit 或运行结果。
- 把历史文档的结论写成当前事实。
- 只写 commit SHA，不说明改动内容。
- 只写“已完成”，不写验证。
- 隐瞒未执行的运行时测试。
- 把 warning 写成 build failure，或把 build success 写成协议验证通过。
- 擅自扩大任务范围。
- 未经授权修改 `src-tauri/`。
- 删除用户已有文件或重置工作区。
- 在交接中留下无法执行的“建议看看”“后续处理”。

---

## 10. 最终交接验收清单

提交交接前逐项确认：

- [ ] 使用当前 HEAD 和当前工作区作为事实源。
- [ ] 记录开始和结束 Git 状态。
- [ ] 没有覆盖用户已有修改。
- [ ] 修改文件和职责已逐项列出。
- [ ] Bug 有根因和触发链。
- [ ] 功能有准确作用域和数据模型。
- [ ] 所有验证命令均为真实执行结果。
- [ ] 未执行项明确标注。
- [ ] Build warning 与 failure 分开。
- [ ] 前端能力和后端契约没有混淆。
- [ ] CSS 与 DOM 同步清理。
- [ ] 错误路径和异步竞态已说明。
- [ ] 下一步可直接执行，无需猜测。
