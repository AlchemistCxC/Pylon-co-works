## 一、目标架构（权威）

### 1.1 一句话
渲染**表现开放给插件**（内容块 + 消息/工具），由**框架无关的表现层**（`RendererRegistry` + `RenderSurface` 命令式桥）承载；**聊天渲染用 SolidJS**（流式/行级更新的性能需求）；**React 保留为应用 GUI 框架**。

### 1.2 为什么两条腿都要
- **为什么聊天用 Solid（D1 的动机）**：React 无法流畅实现**流式输出**与**行级细粒度更新**（每次 token 重渲染整棵/大范围组件树），Solid 的细粒度响应式能在 token 级、按发生变化的节点做最小更新。所以聊天区渲染选 Solid。
- **为什么表现层框架无关（D4）**：表现如何开放给插件、怎么替换，不应绑死具体框架。`RendererRegistry`（查询面）+ `RenderSurface`（命令式 mount/update/destroy/on 桥）是框架无关的——契约明确"宿主把 React 的 MessageRow 或 Solid 的 SolidMessageRow 作为 component 传入"，且契约不 import React/Solid。
- **两者配套**：D4 负责"表现交给插件（框架无关）"，D1 负责"聊天用哪个实现（选 Solid，因性能）"。不冲突。

### 1.3 为什么 React 不删
- 应用 GUI 框架即 React：入口 `main.tsx → KernelRoot → ApplicationMount`。
- 104 个文件 import React：settings(13) / sheets-file(11) / workspace-sheets(7) / chat(11) / plugin-runtime-ui / kernel / sidebar / right-panel / sheets-{search,history,gateway,browser} / components-cc。
- **删 React = 重写整个 GUI**，不可行也无必要。Solid 只替代**聊天区**这一块的渲染。

### 1.4 目标数据流
```
[ACP wire] → chatEventController(归一化) → sessionRuntimeStore(reducer/snapshot)
  → buildChatRowDescriptors(行描述符: RenderMessage + toolVisualState + 连接线)
  → [框架无关渲染表现层] RendererRegistry + RenderSurface 命令式桥
       ├ renderMessage / renderTool / renderReasoning   （消息/工具，插件可换）
       ├ resolveContentRenderer                          （内容块 spinner/footer/plan/content-part，M8 既定）
       └ ContentRendererKind 开放                        （D2）
  → 聊天实现：SolidJS（流式/行级性能）作为首选 / React 聊天链共存退路
  → [React GUI 框架（保留）] ApplicationMount / KernelRoot（设置/sheets/侧栏/kernel）
```

### 1.5 目标特征与验收
| 维度 | 目标 | 现有基础 |
|---|---|---|
| 聊天渲染性能 | 流式/行级细粒度更新流畅 | Solid 细粒度响应式；SolidWorkbench（实验）转正 |
| 表现开放插件 | 内容块 + 消息/工具可插件替换 | Registry + RenderSurface 已存在（M8 待接主链路） |
| 表现层框架无关 | React/Solid 都作 component 传入 | 契约明文（messageRenderer.ts） |
| React GUI | 全保留 | 104 文件依赖，框架不动 |
| kind 扩展 | ContentRendererKind 开放 | resolve 已支持任意值（D2） |
| 消息/工具渲染 | 经 renderMessage/renderTool/renderReasoning | 已深度接入 |

## 二、当前渲染架构（现状基线）

### 2.1 一句话
应用 GUI 是 React 框架；聊天区有 React 实现（ChatView）与 Solid 实验 workbench（SolidWorkbenchApp）。插件注册表做查询面：消息/工具深度经 registry，内容渲染"仅注册元数据 + 组件直连"（M8 第一版既定）。

### 2.2 数据流各层（已逐文件核实）
1. **归一化层**（wire→Message）：`chatEventController.ts`。10 种 SessionUpdate 全到 UI（5 消息行 + 5 会话层类）。**在此丢弃 `locations`、`todos` 数组摘要落空**。
2. **事件 reducer**：`sessionRuntimeStore.ts` → workbench snapshot（Message[]、session state、`createPreviewWorkbenchRuntime` 冻结快照+订阅）。
3. **行描述符**：`chatRowPipeline.ts` → RenderMessage + toolVisualState + showConnector。
4. **插件注册表**：`RendererRegistry` 4 类（message/content/tool/code-highlighter）。
5. **聊天双实现**：
   - **React 生产版**：`ChatView.tsx`→`MessageRendererHost`(:217)→MessageRow/ToolCard；streaming: StreamingThinking/AssistantText；GenerationFooter/TaskTree 组件直连。
   - **Solid 实验版**：`SolidWorkbenchApp.solid`→MessageRendererRow.solid（tool→ToolCard.solid，其它→MessageRow.solid）；InputBar/Widgets/Footer/TaskTree 直连；仅 smoke/demo 挂载（未接生产）。

### 2.3 关键现状事实
- React GUI 框架；Solid 聊天实验宿主。
- `MessageRendererKind = react|solid|webcomponent|unknown`；`presentation.renderer.set` 可切；Solid `experimental:true`（solidRenderer.ts:119）。
- 内容渲染器契约"查询面先行"：plan/footer/content-part 仅注册元数据、主链路用内置组件（rendererContentPoints.ts:35/42/49）。
- `resolveContentRenderer` 目前**仅 ansi 真正消费**（resolveAnsiProvider）；spinner 双轨；plan/footer/content-part 无消费方。
- 字典库（catalog + yaml overlay）决定工具 kind/action/summary。
- Solid 转正基础：13 测试文件 + smoke 基建 + `check:solid`；**Solid 测试已跑在 vitest 主门**（vitest.config include 无 exclude）。

## 三、现状缺口（渲染覆盖调查）

### 3.1 🔴 硬缺口（wire 有、模型/渲染没有）
1. **工具 `locations`**（file:line 引用）— `chatContracts.ts:88` wire 有 `locations?:unknown`；`chatEventController.ts:631/638/731/738/1118/1148` tool_call dispatch 从不提取；`Message`/`ToolPresentationModel` 无字段 → 归一化即丢弃。
2. **多模态 ContentBlock**（image/vision/audio/附件）— `collectToolOutput` 只收 `text`+`tool_diff_content`，其余 block type **静默丢弃**；`content-part` 渲染器注册为空壳（builtinRenderContent.ts:38）。

### 3.2 🟠 粒度/面板缺口
3. **工具 action(14)→kind(7) 坍缩** — `ToolAction` 14 种（含 navigate/click/type/snapshot/delegate/plan/skill），渲染只按 `ToolKind` 7 种（read/edit/execute/search/fetch/think/other）→ 浏览器/交互/委派/技能工具无专门卡。
4. **任意 `config_option` 无通用 UI** — `sessionConfig.raw` 存全量，只消费 model/mode 子集。

### 3.3 🟡 轻缺口（字段已建模、UI 无可见呈现）
5. `Message.time` 从不显示（唯一消费方搜索）；`ToolPresentationModel.inputText` 建模未独立渲染；`PlanEntry.priority`（仅相等比较）不渲染；`OptionalChatEventIdentity` 无可见标签。
6. Solid 链：available_commands 未接 wire（斜杠来自插件注册表）、footer 缺 cacheReadTokens/usage 百分比/bar。

### 3.4 Peri 专属（agent-catalog，16 工具）
- 🔴 `TodoWrite` 数组 `todos` 摘要为空 — `summaryFields:['todos']` 是数组，`firstString`（toolPresentation.ts:23）只取字符串 → 空摘要；且 kind `other`/action `plan` 坍缩通用卡。
- 🟠 `Agent`(delegate)、`ArtifactTool`(write)、`SkillTool`/`DiscoverSkillsTool`(skill) 渲染为通用 read/execute 卡。

### 3.5 已覆盖（无需再投入）
- 10 个 SessionUpdate 全到 UI；plans/modes/slash/usage-token(React)/footer/model widget；tool 的 text+diff+ANSI。

## 四、插件化渲染机制审核

### 4.1 结论
架构为插件化设计、已按"M8 查询面先行"落地；目标是沿 M8 **就地小步推进**，**不是另起炉灶、不是删 React**。所谓 content-part/plan/footer"组件直连"是 M8 契约明文的第一版形态（"仅注册元数据，主链路仍用内置组件"）。

### 4.2 健全部分
- **4 类注册表**（`ReactiveRegistryStore`）：贡献 id 唯一、layer→priority→owner→id 排序、before/after 拓扑约束、成环检测。
- **select**（rendererRegistry.ts:43）：非 fallback 优先于 fallback，同能力按优先级。
- **Shadow 事务**（热替换）：message/content/tool/highlighter 四实体 validate/commit/rollback/revert + replacingRuntimeInstanceId。
- 定义校验（id/priority/fallback/canRender）+ onError。
- **tool `kind:'*'` 通配**（rendererRegistry.ts:185）。

### 4.3 框架无关表现层（已存在）
- `messageRenderer.ts` 契约：RenderSurface 为命令式 mount/update/destroy/on 桥；宿主把 React `MessageRow` 或 Solid `SolidMessageRow` 作为 component 传入；契约不 import React/Solid。
- `rendererContentPoints.ts`：契约层不 import React/Solid。

### 4.4 M8 待推进项
1. ContentRendererKind 仍封闭联合（`ansi|spinner|content-part|plan|footer`）— D2 开放为 string+命名空间。
2. plan/footer/content-part 组件直连（M8 v1）— D4 接入 resolveContentRenderer。
3. content-part 内置空壳（builtinRenderContent.ts:38）。
4. resolveContentRenderer 无通配（vs tool `*`）。

## 五、工具字典一致性（外置覆盖 vs 内置）

### 5.1 字典源
- `shared/agent-catalog.json`（基线：Peri 16/Hermes 20/claude-code 8）→ BUILTIN_TOOL_REGISTRY → registerToolRegistryEntries。
- `agents.yaml tool_dictionary`（外置，后端 `load_tool_dictionary`（agent_config.rs:1218）→ bootstrap `applyPylonToolDictionary` → `registerToolDictionary`）。

### 5.2 问题
- **当前"整 provider 替换"过度**：`registerToolDictionary`（toolRegistry.ts:108）`unregisterToolRegistryProvider(provider)`+全量重注册 → 丢弃外置未列的内置工具（Peri `ArtifactTool` 只在 catalog）。
- **"外置覆盖内置同名字段"是既有设计意图**（注释明文；实测 Peri.Read summaryFields 收窄 `['path','file_path']`→`['file_path']`）。

### 5.3 结论
**不需要"合并唯一字典"（会丢外置覆盖权）；改"替换→按名叠加，工具级覆盖"**：`registerToolRegistryEntry` 本就按名 set（toolRegistry.ts:31）。落点 `registerToolDictionary`(:108) 去掉整删。已核实**无"用外置删内置工具"现用例** → 按名叠加不破坏现有用途。
