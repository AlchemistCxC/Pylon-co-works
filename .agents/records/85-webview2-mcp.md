## 方案要点

### 进程模型

```text
MCP 客户端 ──stdio(JSON-RPC 2.0)──► pylon-webview2-mcp ──CDP/WebSocket──► Pylon.exe (WebView2)
                                     GET /json 做目标发现
```

`Cdp` 由 `Server` 持有并以 `Arc` 共享，WebSocket 会话跨工具调用复用。每个请求单独 spawn
一个 task——`webview_evaluate` 撞上永不 settle 的 Promise 会占满超时窗口，串行处理会让
后续请求陪着一起卡住。

### 值得单独说明的决策

1. **JS 片段不用 `format!` 构造。** 模板里 JS 花括号远多于占位符，逐个转义成 `{{`/`}}`
   是纯手工风险。改用单趟插值 `render()`：最长 key 优先（避免 `{A}` 吃掉 `{AB}` 的前缀），
   且替换进去的值不会被二次展开。全部外部字符串过 `js_str()`。
   包装表达式时 `return (` 之后强制换行再闭合——否则表达式末尾的 `//` 行注释会把 `);`
   一起注释掉。这条有专门用例。

2. **DOM 走自序列化而非 `DOM.*` 域。** `DOM.getDocument` 的 nodeId 会被任何 DOM 变更作废，
   agent 拿着旧 id 调用只会收到 "Could not find node"，而这种现象在排障时会伪装成
   「工具坏了」。自序列化一次往返拿到全部，且没有句柄失效问题。
   `DOM.*` / `CSS.*` / `Emulation.*` 由 `webview_raw_cdp` 兜底。

3. **事件的 scan / limit 双上限。** 要「最近 50 条 error」时中间可能夹着上千条 info，
   只检视 `limit` 条会一条都搜不到；但也不能真把缓冲拉满。故 `limit` 限返回、
   `scan` 限检视（默认 limit×20，上限 3000），返回里给 `scanned` 与 `buffer.evicted`
   让调用方判断窗口是否够大、增量有没有缺口。

4. **游标语义分离。** 省略 `since_seq` → 从上次位置读并推进游标（排障主路径：
   先做动作，再读增量）；显式传 `since_seq` → 不推进游标（无副作用重读）。
   两种读法共用一份缓冲，有专门用例固定这个差异。

5. **网络事件按 requestId 合并，且区分两种写路径。**
   `requestWillBeSent` 走**整体替换**（redirect 链上旧 url 对新一跳已不成立，
   合并会留下自相矛盾的记录，只保留首次 `startedAt`）；
   `responseReceived` / `loadingFinished` / `loadingFailed` 走**就地合并**（保留 request
   阶段的 url/method/headers）。两类写路径都必须经过统一的 `push_network`
   打 `seq`/`updatedAt`，否则会漏掉「缓冲按最后变更时间排序」这条不变量。

6. **`webview_click` 做命中测试。** 返回 `hitIsSelfOrDescendant`——为 false 说明该坐标上
   落的是别的元素，即目标被遮挡。这是「点了没反应」最常见的成因，而 `element.click()`
   永远查不出来。`mode:"dom"` 提供绕过路径，但返回里会说明它绕过了命中测试。

7. **事件订阅状态存页内，不存 Rust 侧。** 页面 reload 会清空 `window.__PYLON_MCP_EVENTS__`，
   Rust 侧的「已订阅」缓存感知不到这个事实，只会让后续 drain 永远返回空。
   以页内为准则天然自愈（订阅幂等，下次调用自动补订阅）。

8. **`evaluate` 不做自动重放。** 重连后重放写操作（如 `emit`）会执行两次。
   只在「会话在调用前就已断开」时不涉及重放；表达式可能已执行时直接报错并说明原因，
   把判断交给调用方。`call` / `call_with_timeout` 则安全地重试一次（调用前也会检查存活）。

9. **工具表用 `&'static str` 类型描述 DSL。** `json!()` 不能在 `static` 里求值
   （`serde_json::to_value` 不是 const fn）——这是第一次编译时暴露的设计错误（709 个错误）。
   改为 `enum:x|y` / `string_or_string_array` 等描述，schema 在 `catalog()` 时构建。
   并有用例断言表里每个描述都在已知集合内：否则打错字会静默降级成 `string`，
   而 schema 依然「合法」。

10. **`webview_targets` 在端点不可达时不报错。** 它是「端口通不通」的探针，
    返回 `reachable:false` + 完整开启步骤 + `isError:false`。
    探针本身失败会让 agent 先去排查探针，而不是排查被探对象。

测试在开发过程中抓到 5 个真实缺陷，均已修复（不是改测试迁就实现）：

1. redirect 链保留了第一跳 URL 而非最后一跳（`network_upsert` 语义错，拆成 replace/merge 两条路径）
2. `--port bad --help` 先报参数错而不是回答 help（改为预扫描短路）
3. `once(` 不在扫描目标里 → `once(...)` 形式的事件名全部漏扫
4. `.emit(` 与 `emit(` 两个 needle 同时命中 → 同一次调用被记两遍
5. 缺少标识符边界 → `reemit(` / `anonce(` / `$emit(` 被误报为事件调用

另有一次**冒烟脚本自身**的断言错误：我把「存在 `id: null` 的报文」当成「回了通知」，
而 JSON-RPC 2.0 规定解析错误的 `id` 必须是 `null`。已改为精确断言
「`id` 为 null **且带 `result`**」。
