## 元信息

- 关联：issue #150 / #148（均已关闭，本轮为「问题本身仍需修」的续修）、ADR-0006（本轮按其「修订」一节扩展）
- 日期：2026-09-17 晚
- 触发：真机 A/B 显示 leaf-graft 之后**残余仍有 276 次整段重解析**（约 269 ms / 一轮回答），用户判定「#148 还是得修一下」

## 目标与范围

**要达成**：把「剩余整段重解析」再压一档，方向由数据定，不猜。

**不做什么**：不上 worker；不引入第三方增量解析器；不做行内容的**片段解析**（markup 行的 inline 解析，见「未解问题」）。

## 方法：先量哪里贵，再测准参考树形状

**量**：从真机那一轮回答的渲染文本统计——4618 字里只有 60 个 ASCII 标点，但**有 116 行**；结合 276 次整段重解析 ⇒ 残余主要来自**换行与行首标记**，不是标点。

**测形状**（逐条实测参考树，决定了拼接能不能写死）：

| 追加形状 | 参考树（实测） |
| --- | --- |
| 段落续行 `A` → `A\nB` | `p > text "A\nB"`——软换行在**同一个 text 节点内**，不是新节点 |
| 无序/有序列表新增一项 | 列表尾部 `"\n"` 被替换为 `["\n", li(内容), "\n"]` |
| 换子弹符 `-`→`*`、换序号分隔符 `.`→`)` | **拆成两个列表** ⇒ 必须回退 |
| 空行开新段落 / 标题后接段落 / 围栏后接段落 | 都在**根级**追加 `["\n", p(内容)]` |
| 列表项 lazy 续行、引用块内续行 | 与段落续行同形（同一 text 节点内的 `\n`） |
| 表格后接文字 | 表格结束另起段落 ⇒ 形状不同，回退 |

## 改动

1. **三条按行拼接规则**（判据见 ADR-0006「修订」一节）：续行 / 同款标记新列表项 / 新段落。
2. **换行归一化**：`/^\n+$/` 的差量是**不变式拼接**（行尾换行与空行是块间分隔，CommonMark 在块尾会剥掉）⇒ 直接复用基座模型；基座自带的尾随换行与差量开头的换行**合并计数**后再走行规则。这一步是真机数据逼出来的：一行边界会先来一个纯 `\n` 差量、再来行内容，原来两次都要整段重解析。
3. 脊线重建泛化：`rebuildChain(chain, depth, edit)`（`edit` 作用于指定层的子节点列表，其余层只替换脊线下标处的子节点）。

## 验证

**逐前缀差分 + 方向性**（`issue150.incrementalGraft.test.ts`，45 条）：

- 37 个夹具**每个前缀**与整段重解析逐块一致（含换款标记、松散列表、缩进续行、表格后接文字、项内含行内元素的列表等高风险形状）；
- 方向性：续行 / 新列表项 / 新段落 / 尾随换行 + 行内容 必须 graft；换款标记、松散列表、缩进续行、表格后接文字必须回退。

**变异核验**：M5（不校验标记同款）→ 2 条红；M7（续行不判落点容器）→ 2 条红；**M6（不看列表是否松散）与 M8（标记行也当续行）未转红**——核对后确认二者在当前判据组合下**不可达**（松散项会让链长变 4 被链长判据排除；标记行必含标点，先被行白名单挡下），属冗余防御，保留但如实记录。

## 结论与建议

- 受控夹具上，增量解析把整段重解析与解析 CPU 压到基线的 **1/9–1/33**；真机上整段重解析占发布数的比例降到 **~26–31%**。
- 真机残留约 **1–3% 单核**（末轮 784 ms 摊在 ~25 s 揭示期；前三轮约 1.6%），主线程**无任何症状**（0 long-task、`publishCost` p95 ≤ 2.2 ms）。
- 剩余成本的来源已经清楚：**带行内标记的行**（`**`、`` ` ``、`|`、`-` 等）与表格行只能回退。再往下需要「片段解析」——把该行交给解析器取回 inline 节点再挂上去（异步、判据面更大）。

**建议止步**：片段解析能再降约 2–3×（真机残留 ~1% 单核量级），但要以异步片段解析 + 更多拼接家族为代价；在这个量级上性价比不足。若仓库主仍要推进，按 ADR-0006 的备选方案单独立项。

## 追加（同日稍晚）· 行内容入口与尾随换行归一化

用户要求继续修「每行仍有一次整段重解析」的残余，本轮补两项（判据见 ADR-0006 修订节）：

1. **行内容入口**：基座已以换行结尾时，**纯内容差量**也交给同一套行规则（真机形态：一行边界先来纯 `\n`，下一帧才来行内容）。
2. **尾随换行归一化**：先把差量**尾部**的换行摘掉再分类——每帧 2–5 字到达时「内容 + 换行」常挤在同一个差量里（`"。\n"`）。

**受控夹具**（同前口径，步长 2）：

| 夹具 | 基线 | 本轮 | 倍数 |
| --- | --- | --- | --- |
| 40 项列表 2931 字 | 1466 次 / 2357 ms | **54 次 / 67 ms** | 27.1× / 35.2× |
| #55 形状 3078 字 | 1539 次 / 2464 ms | **88 次 / 103 ms** | 17.5× / 23.9× |
| 真机同构 5025 字 | 2513 次 / 6861 ms | **160 次 / 536 ms** | 15.7× / 12.8× |

纯文本段落流（996 步）：整段重解析 **1 次**（关掉「行内容」入口会退化到 15 次——步长 1 时多候选基座探测能救回这些形状，故该入口的边际收益在步长 2 才显现）。

**变异核验**：M11（续行时不带换行 = 拼错）→ 9 条红；M12（不做尾随换行归一化）→ 3 条红；M9（关掉行内容入口）→ 1 条红。后两者是**纯性能入口**（退化只是慢、不会算错），所以由新增的两条**成本锁**看守，而不是正确性用例。

**差分测试步长参数化**：真机揭示每帧 2–5 字到达，不同步长会走出不同形状的差量（`" 乙"`、`"2. "`、`"甲\n"`…）。原差分只跑 1 字步长，本轮改为 **1/2/3/5 四种步长**都跑——这是覆盖盲区，补上后 55 条用例全绿。

**真机第五轮**（同一 prompt，回答 7182 字 / 34 块 / 尾巴峰值 3732）：parsed **399**、grafted 696、parseMs **614 ms**、发布 1036 次 ⇒ parsed/publishes = **0.385**；同形状「每发布一次整段重解析」为 1036 次 ⇒ **2.6×**。

**跨轮仍不可比**：五轮回答长度 4.5–10.7 KB、块数 13–59、尾巴峰值 3.4–3.7 KB 各不相同，parsed/publishes 在 **0.26–0.39** 之间摆动——摆动的来源是**内容形状**（带行内标记的行越多，能拼的越少）。受控夹具才是可比口径（12–35×）。

## 追加（同日再晚）· 稳定性加固：随机化差分 + 提升即全量

速度停手后转稳定性（用户要求：「解析可不能错乱」）。三条不变式与各自的证据：

**一、随机化差分（确定性种子）**：手写夹具只能覆盖想得到的形状，而增量判据是否定式的（不含标点、
落点安全、标记同款…）——否定式判据要靠**穷举式反例搜索**。新增
`issue150.fuzzDifferential.test.ts`（8 个固定种子 × 48 记号 × 步长 1/3，失败可复现，随 CI 常跑），
并做了一轮**深度 campaign**（不入库）：**400 种子 × 96 记号 × 步长 1/5 = 92,735 次前缀对照，0 反例**。
字母表含行首标记、围栏、表格、行内标记、自动链接、实体、转义、缩进、硬换行、空行、CRLF、制表、
非 BMP 字符。

**二、提升即全量（自愈）**：原以为「已提交内容一定来自整段重解析」——**实测不成立**：尾块被提升为
稳定行时文本没变，资源不重取，于是已提交内容沿用增量模型（万一某个没预料的形状拼错就不会自愈）。
修法（`MarkdownContent.solid.tsx`）：

- 解析源从「文本」改为 `{ text, cache }` ⇒ 提升（cache false→true）时**换源重解析一次**；
- `StreamingBlockRow.tail` 从普通字段改为**信号**（原来它不可被依赖追踪，换源条件读不到变化）；
- 代价：每块多一次整段重解析（≈0.2–4 ms/块），换来「已提交内容一定来自真实解析」。

**三、块完成的边界（实现细节，值得记）**：**列表块不会在空行处完成**——列表可以有 lazy
continuation，splitter 把整个列表当同一个未完成块，因此列表的「提升」只发生在终态；段落块才会在
空行处被提升。稳定性用例按块类型分别覆盖。

**稳定性用例**（`issue150.stability.solid.test.tsx`，3 条）：

1. 提升即全量：段落块在空行处被提升时 `parsed` +1，最终 DOM 与一次性挂载逐块相同；
2. 同文本同结果：带行内标记与列表的文本，流式（发生拼接）与一次性流式挂载逐块相同；
3. 多行不串味：两个实例共享基座 MRU 并交替增长，各自等于自己的一次性挂载结果且互不泄漏。

比较基准必须是**同路径的流式挂载**：非流式（已提交消息）路径是另一套渲染模型（纯文本整段直排、
不带 `term-plain-text` 类），那是 #55 时代的既有契约——第一次写成「与非流式挂载比对」是错的。

**既有断言的一处更新**（`StreamingMarkdownPerformance.solid.test.tsx`，§4.3）：终态提升多一次解析，
故 `parseCount + 1` 改为 `parseCount + 2`；**高亮次数不变**（代码块高亮结果被复用）。「每个 chunk 不
重解析」那条由同文件上一个用例逐 chunk 锁定，未放宽。
