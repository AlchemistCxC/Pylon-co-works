# Dev Record — #150 真机 A/B：增量 graft 前后对照，与「真流式解析是否必要」的判定

> 入库保留。规格文档（spec）不保留，其中的目标、范围、方案与验收结论在此承接。
> 产出路径：`.agents/records/issue-150-live-ab-before-after.md`

## 元信息

- 关联：issue #150（施工单）、ADR-0006（路线决策）、`.agents/records/issue-150-tail-incremental-parse.md`（开发记录与测试环境数据）
- 日期：2026-09-17
- 目的：在真机（同一台机器、同一 WebView2 引擎、同一 prompt）对照「改进前 / 改进后」，据此判定**真流式解析器**（fork 级改动）是否有必要。

## 方法

| | 改进前 | 改进后 |
| --- | --- | --- |
| 构建 | 用户本地安装版 `F:\A-I\Platform\Pylon\pylon.exe`（md5 `b15a9461…`，早于 #148/#149，**读数无 `parseCost`**） | 本分支 release 构建（md5 `b2480959…`，含 #148/#149/#150），替换同一便携版目录的 exe（`data/` 等不动） |
| 计量 | 尾巴长度曲线 × 发布率积分（推算） | 引擎内 `streamingDisplay.parseCost` 计数器（实测） |
| 采集 | 探针：`long-animation-frame` + `longtask` + 每 500 ms 顶层块长度普查；`streamingDisplay` 的 `snapshot` / `publishCost` | 同左 + `parseCost`（`parsed` / `grafted` / `skipped` / `parseMs` / `maxParseMs` / `maxTextLength`） |

两边都用**同一条 prompt**（30 个短段落 + 40 项无空行有序列表 + 6×4 表格 + 约 1200 字连续段落），各在一个**新建聊天会话**里跑；窗口离屏 1440×900（不弹到桌面、不抢焦点），采样后移除探针并恢复窗口。

## 结果

| 指标 | 改进前 | 改进后 |
| --- | --- | --- |
| 揭示总量 / 顶层块数 | 10763 字 / 59 块 | 4561 字 / 16 块 |
| **最大单块（流式尾巴峰值）** | **3610 字** | **3382 字** |
| 尾巴 >1000 字的时长 | ≈ 25 s（其中 13.5 s 稳定在 1029 字） | ≈ 10 s |
| 发布次数 | 1600（发布间隔中位 21.2 ms ≈ 47 次/秒） | 876（同量级节奏） |
| **解析负载** | 整段重解析字符量 ≈ **1.74M** ≈ **1915 ms CPU**（推算） | `parsed` **276** + `grafted` **507**，`parseMs` = **269 ms**（实测） |
| **每千揭示字的解析 CPU** | ≈ **178 ms** | ≈ **59 ms** |
| graft 命中率 | —（无此机制） | **65%**（507 / 783） |
| `skipped`（同 tick 被取代） | — | **0** |
| `publishCost`（发布步） | p95 3.2 ms / max 3.5 ms | p95 2.0 ms / max 2.9 ms |
| long-task 条数 | **0** | **0** |
| LoAF | 36 条，最大 465 ms，`blockingDuration` **全 0** | 73 条，最大 468 ms，`blockingDuration` **全 0** |

**同形状口径**（消除 LLM 输出长度差异）：改进后那一轮若按「每次发布整段重解析」计，876 次发布 × 尾巴均值 ≈1.7k 字 ≈ 1.5M 字 ≈ 1.6 s CPU；实测 269 ms ⇒ 该形状下 **≈ 5.9×**。

## 判定：真流式解析**没有必要**

1. **残留成本已经很小**：最坏形状（3.4 KB 单块）在一轮 4.5 KB 回答里，解析 CPU 合计 269 ms，摊在约 16 s 揭示期 ≈ **单核 1.7%**；每千揭示字 59 ms。（真流式解析器最多再吃掉剩下的 276 次整段重解析，即再降约 3–5× ⇒ 单核 0.5% 量级。）
2. **主线程没有症状**：两版都 **0 条 long-task**、LoAF `blockingDuration` 全 0、`publishCost` p95 ≤ 3.2 ms。也就是说「每帧重解析」从来没有表现为可感知的卡顿——它只是 CPU 浪费。
3. **代价不成比例**：按 ADR-0006 的分析，真流式解析要 fork micromark（无公开增量 API）+ 永久维护「与一次性解析逐前缀等价」，换来的是把 1.7% 单核降到 0.5% 单核。
4. **两条副证**：① `skipped = 0` —— 生产里没有「同一 tick 内多次发布」，#148 的「最新即胜」判据在真机不触发（与 #141 的调查结论一致，它服务的是测试与峰值场景）；② 两版都出现 465–468 ms 的 LoAF 帧且 `blockingDuration` 全 0 —— 那是离屏窗口被合成器限帧的伪影，与解析无关，用它可以排除「长帧 = 解析卡顿」的误读。

**结论**：保留 graft，`parseCost` 留作现场探针。只有出现下列信号才重新评估（届时按 ADR-0006 的备选方案立项）：`maxTextLength` 长期进入 10 KB 量级、或 `maxParseMs` 逼近帧间隔（≈16.7 ms）、或 `parseCost` 之外的证据显示主线程出现长任务。

## 过程中的其他事实

- 启动恢复会话本身会产生一次性解析开销：本轮新实例启动即 `parsed = 139`、`parseMs = 252 ms`、`maxTextLength = 7425`（回放历史消息走的是非流式缓存路径，`grafted` 保持 0 —— 与「graft 只作用于尾块路径」的设计一致）。
- 采样用的两个会话留在「聊天」列表里（内容是明确的采样 prompt），可随时删除。
- 现场恢复：探针已移除（`__PARSE_PROBE__` 复查 undefined）、窗口恢复为 1200×800 并最小化、**改进后的版本保留安装**（按用户要求把本地应用替换到最新）。

## 局限

- 两轮是两次独立的 LLM 生成，长度不同（10763 字 / 4561 字），故同时给出「每千揭示字 CPU」与「同形状推算」两种口径；绝对次数（`parsed` 276 等）不可跨轮直接比较。
- 改进前那一版没有 `parseCost` 计数器，其解析负载是**推算值**（尾巴长度曲线 × 发布率 × 已标定的 1.1 µs/字），不是引擎内计时；改进后那一侧全部是引擎实测。
- 单机单实例、每个版本各一轮；结论的量级（1–2% 单核、0 长任务）跨轮一致，但精确数值不应当作基准线。
