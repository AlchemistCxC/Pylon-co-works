# ADR-0006 尾块解析增量化的路线：主线程 graft（不上 worker）

> 入库保留。编号顺延，按编号命名。
> 产出路径：`.agents/decisions/0006-streaming-tail-incremental-parse.md`

- **日期**：2026-09-17
- **状态**：已采用
- **关联**：issue #150（施工单）、#148（解析请求最新即胜）、#141（调查）

## 背景与约束

流式增长尾块每收到一个新文本就整段重解析一次（`markdownRenderModel.ts` 的 `buildMarkdownRenderModel`），单个块揭示期间的总解析量约 `N²/4` 字符。真机实测（#150 评论）：一个 3368 字的单块（40 项无空行列表）累计解析约 2.8M 字符 ≈ 3 秒 CPU，是整块一次解析（3.7 ms）的约 800 倍。

约束（来自 #150 的目标结构与仓库既有契约）：

- 渲染结果必须与整段重解析**逐块一致**；骨架态（P57 S3-R8）、行集合（#55）、`cache: false` 绕 LRU（P57 S3-A11）、解析请求最新即胜（#148）四条契约不变。
- 既有行为测试零修改；新增差分测试必须能在**现有测试环境（vitest + jsdom）**里跑。
- 不改发布节奏，不新增白名单豁免。

## 备选方案

| 方案 | 否决理由 |
| --- | --- |
| **B · 解析搬进 Web Worker（离线程）** | **不减少总 CPU**——只是把同样多的解析挪到另一个线程；而实测症状是浪费（3 秒 CPU/长块）而非主线程卡顿（0 条 long-task、`publishCost` p95 3.6 ms、每帧解析 1–4 ms 落在 16.7–33 ms 帧预算内）。且 jsdom 没有 `Worker`，生产路径在现有测试环境里无法覆盖，需要额外发明测试 harness。 |
| **C · 长尾限频（每 N 帧解析一次）** | 只按常数因子降成本（3–6×），不改 O(N²/4) 的量级；且以「渲染滞后」换成本，属于可见性折中。作为降级手段保留，不作主路线。 |
| **真·流式增量 parser（引入第三方增量实现）** | 没有成熟可用的增量 markdown 实现（remark/micromark 均无公开增量 API），等于自研，风险面远大于收益。 |
| **A · 主线程 graft（采用）** | 见下。 |

## 决定

采用 **A：尾块路径的增量 graft**，只在**不走缓存**（`cache: false`，即增长尾块）的调用上生效。

**判据（全部成立才 graft，否则回退整段重解析）**：

1. 新文本是基座文本的**严格后继**（`text.startsWith(base.text)`），差量 `delta = text.slice(base.text.length)` 非空；
2. `delta` 不含任何可参与 markdown 构造的字符：ASCII 标点、控制字符、`\n` `\r` `\t` 一律禁止（只允许 ASCII 字母/数字、半角空格、以及全部非 ASCII 字符——CommonMark 的行内/块级构造全部由 ASCII 标点触发，行尾只认 U+000A/U+000D）；
3. 基座文本**不以换行结尾**（行首是块级构造的触发位）；
4. 基座模型的**最右叶子是 text 节点**，且 `base.text.endsWith(leaf.value)`（文档末尾确实落在这个文本节点**内部**；以 `**`、`` ` ``、`|` 等收尾时该判据自动失败）；
5. 该 text 节点的**祖先链只含块级/普通容器**（`p` / `li` / `td` / `th` / `h1`–`h6` / `blockquote` / `div` / `span` …），链上出现 `a` / `code` / `strong` / `em` / `del` / `img` 等行内元素即回退（追加会改变该元素的语义或属性）；
6. 该 text 节点**末尾 32 字**不含 ASCII 标点（防 GFM 自动链接被延长、实体/转义被补全——这类构造由尾部的 `:` `/` `.` `@` `&` `\` 等触发）。

graft 本身是纯函数：沿「每层最后一个子节点」的脊线拷贝到该 text 节点并拼接 `delta`，其余子树结构共享（O(深度)）。基座保存在模块内的一个小 MRU（文本 → 已解析模型），只由尾块路径写入。

### 修订（2026-09-17 晚）· 追加「按行拼接」

第一版把「含换行的差量」一律回退，真机对照（`.agents/records/issue-150-live-ab-before-after.md`）显示残余的整段重解析**主要由换行与行首标记贡献**（一轮 116 行的回答里 276 次整段重解析）。据真机参考树形状（逐条实测，见 `.agents/records/issue-150-line-splice.md`）追加三条**结构拼接**规则，仍走同一「判据成立才拼、否则回退」的口径：

| 规则 | 差量形状 | 动作 | 关键判据 |
| --- | --- | --- | --- |
| 续行 | `\n` + 非标记纯文本行 | 延长落点 text 节点（软换行在模型里就是同一节点内的 `\n`） | 落点父节点是 `p`/`li`；基座不以换行结尾；叶子尾部守卫 |
| 同款标记新列表项 | `\n` + **同款**标记 + 纯文本 | 列表尾部 `"\n"` 换成 `["\n", li(内容), "\n"]` | 标记同款（换款会拆列表）、链长恰为 3、项内无 `p` 包裹（松散列表形状不同） |
| 新段落 | 空行 + 非缩进纯文本行（或标题后的单换行 + 行） | 根级追加 `["\n", p(内容)]` | 根级最后一个是元素 |

三条都把「行内容」限制在同一份白名单里，因此单行不可能自成块级构造；换款标记、松散列表、缩进续行、表格后接文字等形状一律回退。该修订不改变上面第 1–6 条对「纯文本追加」的判据。

**换行的三处归一化**（同一修订内补入，均由真机形态倒逼）：

- **尾随换行差量 = 不变式拼接**：文档末尾追加 `\n`/空行不改变模型（块间分隔，CommonMark 在块尾剥掉）⇒ 直接复用基座模型；
- **差量尾部的换行先摘掉再分类**：每帧 2–5 字到达时「内容 + 换行」常挤在一个差量里（`"。\n"`），摘掉尾部换行后内容照常走拼接；
- **基座已以换行结尾时，行内容按行规则拼接**：把「基座尾随换行数 + 差量首部换行数」合并成 `newlines` 交给同一套规则（步长 1 时多候选基座探测也能救回这些形状，故这一条在步长 2 下才显著：同一夹具的整段重解析从 15 次降到 1 次）。

这三条都是**纯性能入口**：退化掉只会变慢、不会算错，因此由**成本锁**（见 `issue150.incrementalGraft.test.ts` 的两条成本用例）而不是正确性用例看守。

## 后果

- **正面**：连续的纯文本追加（流式揭示里约 9 成的发布）从「整段重解析」变成 O(Δ) 的拼接；结构字符（换行、列表标记、行内标记…）到达时仍走整段重解析，因此代价从 `O(N²/4)` 降到「与块内结构边界数成正比」。真机那个 3368 字列表块的整段重解析次数从约 1684 次降到约 100 次量级（见证据）。
- **负面**：判据是多条否定条件，读起来不如「一律重解析」直白；需要在模块里保留一个小 MRU（内存上限见 spec）；graft 命中时**不会**产生 `parseMs`（读数里表现为 `parsed` 下降、`grafted` 上升——这是设计意图，不是漏计）。
- **风险**：判据漏掉某类「纯文本字符也能改变前文解析」的构造 ⇒ 渲染与整段重解析不一致。防线是**逐前缀差分测试**（对全部夹具文本的每个前缀断言 graft 序列 == 整段重解析），以及守门判据的保守取向（宁可回退）。回滚 = 去掉 `incremental` 选项（调用点无需改动：尾块路径默认启用，`incremental: false` 即旧行为）。

- 施工与验收：`.agents/records/issue-150-tail-incremental-parse.md`（差分测试、变异核验、真机形状的解析次数对比）。
